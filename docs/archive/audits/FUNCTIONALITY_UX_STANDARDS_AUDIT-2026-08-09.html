Historical audit snapshot from August 9, 2026. Findings are not a current open-issues list.

AwardOS · Pass 2 · Functionality, UX & Standards

The app is feature-complete on the surface and unsafe underneath.

A read of all 137 source files, tracing every core feature end to end. The headline is not a UI problem: one live defect makes a public election unrunnable, and three more silently produce wrong vote counts. Deduplication — the product's signature feature — does not deduplicate the ballot.

Files read137 Findings63 Blocker / Critical9 Vote-integrity6

Read this before anything else

Every ballot is deduplicated by IP address alone, for all three verification modes. src/app/api/public/events/[slug]/votes/route.ts:53 sets deviceFingerprint = hashIP(ipAddress, slug) — no canvas, no WebGL, no screen or timezone signal, despite the field name and the PRD's definition of a device fingerprint. A partial unique index on (event_id, device_fingerprint) then enforces it in the database.

On campus Wi-Fi, an office network, or a mobile carrier's NAT, the first person to vote locks out everyone behind that IP. They are told "A ballot from this device has already been submitted." For the MVP's stated target — university award nights, 90%+ mobile traffic — this does not degrade the product, it ends the event. The PRD anticipated exactly this (EDGE-VOT-06) and the shipped behaviour is the opposite of what it specifies.

It also fires in EMAIL_OTP and INVITATION_CODE mode, where the fingerprint is still written and still indexed — so two verified voters sharing a lecture-hall network collide even though each holds a valid, distinct credential.

Vote integrity & counting

F-01"Device fingerprint" is only a hashed IP — one vote per networkBlocker
Where
api/public/events/[slug]/votes/route.ts:53, lib/hash.ts:17, lib/db/schema/voting.ts:49–51, migrations/0001_vote_integrity.sql:4
Now
Fingerprint = sha256(ip + slug). A unique index rejects the second ballot from any IP, in every verification mode.
Should
Either collect a real client-side fingerprint, or scope the constraint to NONE mode only and treat IP as a rate-limit signal rather than an identity. PRD FR-VER-01 lists canvas, WebGL, timezone, screen resolution — none are collected anywhere in the codebase.
Impact
Blocks the core flow for the majority of real voters.
F-02Disqualified nominees still count toward vote percentages and ranksWrong counts
Where
actions/results.ts:44,62–63,85,92–101
Now
totalCategoryVotes sums votes for every nominee row, including DISQUALIFIED, MERGED and REMOVED. The filter at line 85 excludes only MERGED/REMOVED from the ranked list — disqualified nominees stay in it and are assigned rank: idx + 1.
Should
Disqualified nominees are excluded from the denominator and skipped when assigning ranks.
Impact
Every published percentage is understated. If the top vote-getter is disqualified, the real winner is labelled rank 02 and the public results page shows no winner at all ((public)/e/[slug]/results/page.tsx:152 looks for rank === 1 AND not disqualified — that row does not exist).
F-03Approving a merge does not remove the duplicate nominees from the ballotFeature broken
Where
actions/cleanup.ts:182–269 and :332–520 (bulk)
Now
Nominee rows are created by syncNomineesForEvent at submission time — "Jane Doe", "Dr. Jane Doe" and "J. Doe" become three ACTIVE rows. Approving a merge re-points nominations.resolvedNomineeId and creates/updates one canonical nominee, but never sets the source nominees to MERGED. nominees.mergedInto exists in the schema and is never written anywhere in the codebase.
Should
Source nominees flip to MERGED with mergedInto set, so the ballot query (actions/voting.ts:363, filtering status = 'ACTIVE') drops them.
Impact
The ballot still shows all three spellings after cleanup. The deduplication feature has no effect on the thing it exists to fix, and votes split across duplicates. The UI at events/[id]/ai-cleanup/page.tsx:500 explicitly promises "precise tally computation."
F-04Merge re-pointing silently no-ops on any name whose casing was normalisedSilent failure
Where
lib/ai/cleanup.ts:129 produces sourceNominees from normalizeCapitalization(...); actions/cleanup.ts:244–254 matches those strings against raw nominations.nomineeText.
Now
Suggestions carry normalised names ("Jane Doe"); the UPDATE matches on raw submitted text ("JANE DOE", "jane doe"). Any nomination whose original casing differed never matches, so resolvedNomineeId stays null.
Should
Match on a normalised comparison, or store nomination ids on the suggestion instead of free text.
Impact
Merges report success and partially do nothing. Because casing variation is the single most common form of duplication, this likely affects the majority of merges.
F-05Merge inflates nomination counts; undo leaves an orphan nomineeData drift
Where
actions/cleanup.ts:211–217 (inflate), :286–330 (undo)
Now
Approve adds sourceNames.length to a nominee whose count already included those nominations from the initial sync — double counting. Undo nulls resolvedNomineeId and resets status to PENDING, but does not delete the nominee it created or reverse the count bump; the orphan stays ACTIVE on the ballot. The schema's UNDONE status is never used.
Impact
Nomination counts drift upward with each run. Undo is not a true inverse — PRD FR-AI-08 requires it to restore original records.

Where
actions/workspaces.ts:95–107
Now

Phase 3UI/UX & modern standards

The voting experience — highest stakes

Judged as a first-time mobile voter arriving from a WhatsApp link. The visual design is competent and clean; the problems are trust, feedback and mobile ergonomics.

U-01The floating action bar covers the ballot on mobileBlocker

e/[slug]/vote/page.tsx:519 — a fixed pill at w-[90%] max-w-3xl holds a counter, two lines of text and a "Review & Submit Ballot" button in one non-wrapping flex row. At 360–390 px this overflows; the button is clipped or pushed off-screen. Nominee cards are md:grid-cols-3, so on mobile they stack into a long column — with 90%+ mobile traffic, this is the primary voting surface and it is the least tested one.

Modern pattern: a stacked sticky bar with safe-area insets, the count as a slim progress track, and a full-width primary button.

U-02Nominee cards are unreachable by keyboard and invisible to screen readersA11y

e/[slug]/vote/page.tsx:474–481 — selection is a bare <div onClick>: no role="radio", no tabIndex, no aria-checked, no keyboard handler, no fieldset/legend grouping the category. A keyboard or screen-reader user cannot cast a vote at all.

Compounding it: select-none on the page root (:270) blocks text selection sitewide, so a voter cannot copy a nominee name or their own receipt token; body text is text-xs (12px) and text-[10px] throughout, below the 16px that prevents iOS input zoom and well under comfortable reading size; focus:outline-none appears on every input with only a border-colour substitute. PRD §7.5 commits to WCAG AA.

U-03A failed submission can lose the whole ballotData loss

e/[slug]/vote/page.tsx:165–215 — selections live only in React state. There is no retry, no exponential backoff, no offline queue, and nothing persists the payload. A dropped connection on submit discards every selection; the voter must start over. PRD EDGE-VOT-01 specifies three retries plus local replay.

The review modal (:551) is also a hand-rolled dialog with no focus trap, no Escape handler and no scroll lock, and its selections list is capped at max-h-48 — with more than ~4 categories the voter reviews their ballot through a 190px window.

U-04Trust claims the system does not deliverCredibility

The voting surface leans hard on cryptographic language it cannot back: "Cryptographic Ballot Receipt" (thank-you:94), "encrypted, write-locked" (:84), "verify … cryptographic inclusion" (:125), "Encrypted Voting & Anti-Bot Protection" in the global header ((public)/layout.tsx:25). The receipt is a plain session token in a normal column; nothing is encrypted beyond TLS; no bot detection exists.

Given F-08 leaves most voters with no receipt at all, the gap between claim and delivery is exactly where a sceptical voter looks. For a product whose stated purpose is closing a trust deficit, understating and delivering beats overstating.

U-05Verification flows have no resend, no cooldown feedback, no progressFriction

OTP screen (vote/page.tsx:350–392): no resend button despite FR-VER-02 allowing three, no countdown to expiry, no inputMode="numeric" or autoComplete="one-time-code" (so mobile shows a text keyboard and iOS cannot autofill), no paste-friendly segmented input. The invitation-code screen says "8-character" (:403) while INVITATION_CODE_LENGTH is 10 and the generator adds an optional prefix — the copy is wrong and the button stays disabled until 10 characters, so a user typing the 8 they were told to expect sees a dead button with no explanation.

Design system & consistency

U-06The design system exists and 22 of 24 pages ignore itSystemic

globals.css:20–44 defines a complete semantic token set with a dark override, and its own comment states components "should reach for these." Only (dashboard)/integrity/page.tsx and the shell (layout, header, sidebar, toast) comply. Everything else hardcodes bg-white, text-slate-900, border-slate-200/80.

Consequence: a ThemeToggle ships in the header, but dark mode is broken on nearly every page. Worse, four pages are styled dark on the light shell and are currently unreadable: events/[id]/results (:168 text-white), events/[id]/invitations (:208), events/[id]/integrity (:567), events/[id]/branding. nominations/page.tsx:213–272 renders white text on a white card — invisible today. header.tsx:91–124 mixes tokens with zinc-800/zinc-300 in the same dropdown.

U-07The base Card applies a class that does not existSystemic

components/ui/card.tsx:17 applies glass-card. Verified: defined nowhere in the codebase. Open questions — flagged rather than guessed

Q1 · Duplicate voter policy What should happen when two legitimate voters share an IP? The answer determines whether F-01 is fixed with a real client fingerprint, a per-mode constraint, or by making advanced verification the default for public events. This is a product call, not a technical one.
Q2 · Merge semantics Should approving a merge deactivate the source nominees (my read of intent, and what the ballot needs), or is the current nomination-level re-pointing deliberate with nominee cleanup planned elsewhere? The mergedInto column suggests the former was intended.
Q3 · Workspace-level pages Should /analytics, /results, /exports, /branding become genuine cross-event roll-ups, or be retired as redundant navigation? Their titles promise aggregation; the code is a list of links.
Q4 · Scope of MVP Official Results, Community Archive, custom-role permissions, ownership transfer, judge scoring and bot detection are all specified and effectively unbuilt. Which are launch-blocking versus post-launch? This determines how much of Batch 5 is real work.
Q5 · Stage automation autoTransition exists on every stage and no scheduler reads it. Should stages advance automatically (PRD FR-EV-05), or is manual control the intended model? Affects whether F-25 is a correctness fix or a scheduling feature.
